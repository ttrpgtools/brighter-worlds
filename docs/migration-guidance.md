# Finding and moving existing sheets

The canonical home is `https://brighterworlds.app`. Both home pages and both character libraries link to `/migrate`, regardless of whether the library already contains characters. The root library has the primary **Find sheets from the old site** popup action in a prominent callout. The dev callout explains that existing sheets can still be used there.

**Don’t show this again** dismisses the callout on both pages and remembers that choice in localStorage for this browser/profile and origin. It does not change character data or account preferences. When localStorage is unavailable, the current visit can still be dismissed. The `/migrate` guide remains directly accessible.

`/migrate` is an account-free guide and recovery entry point on both origins. On dev it retains local-character selection, companion preview, explicit copy confirmation and standalone file download. On root it offers the same popup action as the library. Both versions expose **Backups and recovery** directly, including ordinary backup/restore and the private recovery archive. No sign-in or online storage check gates those controls. Opening the guide does not upload sheets or delete originals.

The browser and profile that holds the source data must open that source origin. Root cannot scan dev storage, other devices, or other profiles. Signing in on one origin does not sign in on the other. Signing in does not upload local sheets. Account and file paths remain supported alongside the primary same-browser popup path.

## No-loss routes for the three starting states

Use copies of the executable fixtures under `src/lib/data/sheet-format/fixtures` in isolated browser profiles for release verification. Never seed a user's everyday profile. Automated storage/protocol tests use isolated fake IndexedDB databases and fake peer windows; they do not establish live cross-origin browser compatibility.

For an account route from any source: sign in there, open each local character's storage menu, choose **Save online…**, and review the linked group. Wait for every member's **Saved online** result. Partial saves retain drafts and transfer progress; resolve the reported problem and use **Retry transfer**. Then open root and sign into the same account, checking all characters and companions there. The source's original local records remain in recovery archives after promotion to an account identity. Account saving currently rejects embedded-image groups and unresolved companions; retain a file backup instead of discarding content to force a save.

An `exists` response is not a migration receipt. `account-persistence.ts` fetches the existing document and compares canonical portable content before acknowledging it; divergent content becomes a conflict. Popup/file import similarly compares existing content or verifies a content-bound receipt. An **already applied** receipt means an earlier transfer committed; it does not assert that a subsequently edited/deleted destination still matches the source. Retrying must not overwrite newer edits or resurrect deleted copies. Review the current destination when deciding whether a new linked copy is wanted.

## GM backup scope

Direct popup and account transfer cover PCs and linked companions. For GM material use **Download game backup** on the source, then ordinary file restore on root. Its nine categories are custom NPCs, custom relics, encounters, playmat, scenes, custom tables, friends, GM roll log and player activity log. It also includes local characters/companions. Account sheets require a separate owner-scoped character/group download.

Existing GM categories are kept by default. Replacement is explicit and archives the previous category; close other app tabs before replacing categories. Supported embedded images are included; remote image URLs remain references. Backup warnings identify incomplete or unsupported content. Portable files exclude Discord settings, auth credentials and local preferences. **Advanced recovery** creates a separate private archive of readable originals, potentially including webhooks, for manual recovery; it is not an ordinary restore file. See [backups.md](backups.md) for bounds and image details.

## Failures and recovery access

- Auth/storage-service outage: open either origin's `/migrate` directly. It skips ordinary account verification, including with an existing auth cookie. Local selection, direct copy and file tools do not require cloud availability. Existing local deep links remain supported.
- Popup blocked, closed, disconnected or timed out: source copies remain. Retry from root or download the selected backup on dev. Root can also download a fully validated received backup. Use smaller selections if the 16 MiB / 1,000-sheet bound is reached.
- Browser storage denied, quota exhausted, corrupt records or missing companions: do not clear browser data or close an unsaved sheet. Review per-record warnings. Use **Backups and recovery → Advanced recovery**, or **Download original records (private)** when the recovery banner appears. A failing storage API can limit what is readable; check archive warnings and retain open sheets for their own backup.
- Interrupted batch: account saves report per-sheet outcomes and retain partial progress. Popup/file graphs commit atomically; a failed transaction is not reported as copied. Retry the same selection/file to use verified receipts. Verify all outcomes before relying on the destination.

## Validation and routing boundary

Automated coverage is in `sheet-recovery.test.ts` (historical root, source retention, divergence and failed writes), `sheet-backup.test.ts` (historical dev/root formats, companions, files and GM scope), `sheet-transfer/transfer.test.ts` (source consent, conflicts, durable receipts, failures and retries), `account-transfer.test.ts` / `account-persistence.test.ts` (matching/divergent IDs and partial saves), and `server/transfer-access.test.ts` (root/dev landing, migration and deep-link access without account services; migration access with a failing verifier).

The current local server can verify rendering, navigation and account-unavailable recovery controls. The exact two-origin popup/account matrix, Chrome/Firefox/Safari behavior, privacy/opener restrictions and deployment configuration remain the separate dev-first rollout gate. Do not interpret local rendering or fake-window tests as that release evidence.

No redirect, hosting rule or auth callback was changed. Preserve dev `/migrate`, auth completion handling and all character deep links. A future redirect of dev `/` alone needs a separate prepared routing change and validation; no blanket dev redirect is authorized or implemented here.
